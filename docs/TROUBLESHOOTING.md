## 1. 仿真窗口打开、但世界静止不动、`/odom` `/lidar3d` 一个都没有

**最典型的误判**：以为模型没生成 / 桥接没配好。实际是 **Sensors 渲染线程初始化失败，把整个仿真循环卡住了**。

证据（`~/.ignition/gazebo/log/<时间戳>/server_console.log`）：

```
20:30:13.257 [Dbg] [Sensors.cc:258] Waiting for init        ← 卡在这里
...
20:31:07.106 [Dbg] [Sensors.cc:284] Rendering Thread initialized   ← 直到按了 Ctrl-C 才初始化
20:31:07.106 [Dbg] [Sensors.cc:425] SensorsPrivate::RenderThread stopped
```

同时终端里有：

```
libEGL warning: egl: failed to create dri2 screen
```

也就是 54 秒里物理一步都没走（sim_time 不涨、RTF 无输出、所有传感器话题都没有数据）。

**原因**：gz 的 `Sensors` 系统在 server 进程里用 EGL 建渲染上下文；本机 glvnd 默认挑到 Mesa，
Mesa 建 dri2 screen 失败 → 渲染线程不 init → `Sensors` 阻塞整个 world。

**修法（按顺序试）**：

```bash
# ① 强制 EGL 走 NVIDIA（launch 默认已经是这个）
ros2 launch launch/depot_sim.launch.py gui:=true egl_vendor:=nvidia

# ② 换成 ogre 1.x 渲染引擎（走 GLX，不走 EGL），需重新生成世界
sed -i 's/^render_engine: ogre2/render_engine: ogre/' config/world.yaml
make world
ros2 launch launch/depot_sim.launch.py gui:=true egl_vendor:=none

# ③ 软件渲染兜底（慢，但一定能出图；用来确认数据链路本身没问题）
ros2 launch launch/depot_sim.launch.py gui:=true software_render:=true
```

**判定是否修好**（不用看画面）：

```bash
# 注意：没有发布者时 `ign topic -e` 会永久阻塞，一定要包 timeout
timeout 5 ign topic -e -t /lidar3d -n 1              # 有输出 = 渲染通了
timeout 5 ign topic -e -t /world/depot/stats -n 1    # 看 real_time_factor / iterations

# 或者一条命令全查（推荐）：
python3.10 scripts/gz_probe.py
```

## 2. `/odom` 订阅不到（但 `ros2 topic list` 里明明有）

`ros_gz_bridge` 对传感器/里程计类话题常用 **BEST_EFFORT** 发布；脚本里用默认 **RELIABLE** 订阅时
QoS 不兼容，**一个字节都不投递也不报错**。

修法：所有订阅端统一申请 BEST_EFFORT（`qos_profile_sensor_data` 语义）。本仓库
`scripts/preflight.py`、`m1_velocity_tracking.py`、`m2_side_dock.py`、`odom_tf.py` 都已经这样写。
BEST_EFFORT 订阅同时兼容 RELIABLE 和 BEST_EFFORT 的发布者。

## 3. 话题名对不上：`/model/depot_bot/odom` vs `/odom`

`ros_gz_bridge` 的 **ROS 侧话题名 = 参数里写的那串本身**。而 gz 侧的命名规则不统一：

```
cmd_vel / odom      -> 插件内部拼成 /model/depot_bot/xxx，没有参数可改
joint_states        -> 由 URDF 里 JointStatePublisher 的 <topic> 指定（就是 /joint_states）
相机 / rgbd / lidar -> 由 <sensor><topic> 指定（本仓库显式写死，不依赖 link 名）
```

修法：在桥接节点里统一 remap 到 Nav2 / 脚本认的名字（见 `launch/depot_sim.launch.py`）。

另注：`ign sdf -p` 会把 fixed joint 的子 link **合并进根 link**（`base_footprint`），
所以按 `link/xxx_link/sensor/...` 拼话题路径会拿到空话题；必须用 `<topic>` 显式指定。

## 4. MecanumDrive 参数写错不报错，只是车不动/乱滑

Fortress 6.18 只认这些（用 `strings libignition-gazebo6-mecanum-drive-system.so` 核对）：

```
front_left_joint / back_left_joint / front_right_joint / back_right_joint
wheel_radius / wheel_separation / wheelbase / odom_publish_frequency / odom_topic / tf_topic
```

`rear_left_joint`、`left_wheel_radius`、`wheel_base`、`publish_odom` 这些是 DiffDrive 的名字，
写进来会被**静默忽略** → 插件拿不到关节 → 不发布 odom、不发 TF，日志里只有：

```
Error [Element.cc:1018] Missing element description for [back_left_joint]
```

防线：`tests/render_robot.py` 里有参数白名单检查（4 个关节必须映射到真实关节、不允许未知参数）。

## 5. 世界里的东西会倒 / 会被推走

SDF 里 `static` 是**元素**不是属性：

```xml
<model name="x"><static>true</static>...</model>   <!-- 对 -->
<model name="x" static="true">...</model>          <!-- 错：gz 只 warning，然后当动态刚体 -->
```

解法：`scripts/verify_world.py` 的 **A5 全部实体 static** 硬检查，生成阶段就拦住。

## 7. `/odom` 一条消息都没有：MecanumDrive 在这个 6.18 构建里不发 odometry

**现象**：插件加载成功（日志 `MecanumDrive subscribing to twist messages on [/model/depot_bot/cmd_vel]`），
`ign topic -i -t /model/depot_bot/odom` 也能看到 publisher，但 `ign topic -e` 与 ROS 侧 `/odom` 都是零消息。

**对照实验（决定性）**：官方例程 `/usr/share/ignition/ignition-gazebo6/worlds/mecanum_drive.sdf`
单独跑，加不加 `<odom_publish_frequency>50</odom_publish_frequency>` 都一样 —— 车能走（x 0 → 4.32 m），
odom 依然静默。另外自己往 `/test_odom` 发一条 `ignition.msgs.Odometry`，`ign topic -e` 能正常回显 ——
排除"echo 工具坏了"。结论：**这个构建的 MecanumDrive 不发 odom**，不是我们 SDF 写错。

**修法**：`scripts/mecanum_odom.py` 从 `/joint_states` 的四个轮子积分出 `/odom` + TF。
信息源和插件本该用的完全一样（轮角/轮速），不碰 ground_truth。

**两个实现细节（都踩过）**：
- 用 **累积轮角差分**，不要用"轮速 × dt"：dt 版本在 RTF≈0.5 时有 5% 样本因 dt 越界被丢弃。
- `/joint_states` 在 ROS 侧是**真的**带 `position`/`velocity`（gz `msgs.Model` → `JointState` 的转换是对的），
  所以不用碰 gz 的原始 protobuf。

**符号约定（实测标定，cmd → 四轮 rad/s，r=0.076，lx+ly=0.41）**：

```
vx=0.30 -> (+,+,+,+) 3.9474     vy=0.30 -> (-,+,+,-) 3.9474
wz=0.50 -> (-,+,-,+) 2.6974     斜行(vx=vy=0.3) -> (0,+,+,0) 7.895
```

## 8. 横移指令下轮子转、车不动：URDF 的 `<mu1>/<mu2>` 被 `gz sdf -p` 静默丢弃

**现象**：`cmd vy=0.3` 时四轮按 (-,+,+,-) 转得很标准，但**真值横向位移 0.000 m**（误差 -100%）。

**根因**：`robot/depot_bot.urdf.xacro` 里写的是经典的
`<gazebo reference="wheel_*_link"><mu1>0.85</mu1><mu2>1.70</mu2>...</gazebo>`。
最小实验证明这套写法过不了转换：

| URDF 里的写法 | `gz sdf -p` 结果 |
|---|---|
| `<mu1>/<mu2>` 直接子元素 | **整块丢弃**，collision 里没有 `<surface>` |
| `<friction><ode><mu>..` 嵌套 | 被塞到 `<link>` 层（SDF 非法位置），同样无效 |

没有摩擦 = 各向同性 = 圆柱轮只能沿滚动方向出力 → 横向永远没有力。

**修法**：`scripts/patch_robot_friction.py` 在 SDF 生成后给四个轮子注入
`<surface><friction><ode>`：`mu=3.0 / mu2=0 / fdir1=±(1,∓1,0)`（对角同向），
`make robot` 里已固化，并且注入后立刻 `--check`（任一轮没有 `<surface>` 就非 0 退出）。

**效果（真值，不是 odom）**：

```
无 fdir1    vy 0.30 -> 真值 0.000 m/s   (-100%)      // 原地空转
有 fdir1    vy 0.30 -> 真值 0.300 m/s   (-0.1%)      // 横移真的出来了
```

## 9. 判据必须按"仿真秒"算，不能按墙钟秒

**现象**：preflight 判 `2 频率` FAIL（lidar 4.0 Hz / imu 105 Hz）和 `7 直行` FAIL（2 s 只走 0.186 m）。

**根因**：RTF≈0.5 时 1 墙钟秒 = 0.5 仿真秒。lidar 实际是 10 Hz（仿真时间），2 s 墙钟里只推进了 ~1 s
仿真时间，位移自然只有一半。**用墙钟时间去判仿真里的物理量，会把正常场景判成故障。**

**修法**：`preflight.py` 用 `/clock` 算仿真时间 —— `hz_sim()`（按消息 header 的仿真时间戳算频率）、
`spin_sim()`（按仿真时间推进测试窗口）。判 `7 直行` 时期望位移 = `vx × 实际推进的仿真秒数`。

**同一类坑还有两个（都改过了）**：
- `_on_clock` 只往 `clock_stamps` 记账、没往 `stamps` 记账 → `/clock` 明明在发也被判"没数据"。
- 真值复核的**采样窗口**：在停车后取终点、把起步加速段算进 dt，会让速度系统性低估 ~30%
  （0.4 m/s 量成 0.247）。改成运动过程中连续采样、丢掉前 25% 起步段再差分，误差回到 0.1%。

## 10. `pkill -f launch` 杀不干净：bridge / 节点会活成孤儿

**现象**：重启仿真后 `ros2 topic list` 里 `pubs=3`，preflight 的判据开始报奇怪的结果 ——
其实是**三个 bridge、两个 mecanum_odom** 同时在往同一个话题发（前几次 launch 的子进程没死）。

**根因**：`ros2 launch` 的子进程（`parameter_bridge` / `robot_state_publisher` / 我们自己的脚本）
不一定是它的子 shell 被杀时一起退的；`pkill -f "<launch 文件>"` 只杀 launch 本身。

**修法**：重启前一条命令全清（`magic` 在方括号，避免 pkill 匹配到自己）：

```bash
pkill -f "[p]arameter_bridge" ; pkill -f "[m]ecanum_odom.py" ; pkill -f "[o]dom_tf.py" ;
pkill -f "[r]obot_state_publisher" ; pkill -f "[d]epot_sim.launch.py" ; pkill -f "[w]arehouse.sdf" ; sleep 5
```

**注意**：如果这条命令后面还跟着 `pgrep -af "parameter_bridge|mecanum_odom|..."`，
那个**不带方括号**的匹配串就在自己的命令行里 → pkill 会把自己也 SIGTERM 掉（实测踩过，
表现为"命令返回 -15、什么都没输出"）。检查用的 pgrep 也要方括号化，或者另起一条命令。

## 13. odom 的 yaw 记少了：轮角在 ±π 处缠绕

**现象**：`make odom-yaw`（正反各转 2 s，wz=±0.5）——

```
正的 wz=+0.5: 真值 Δyaw=+57.0°   odom Δyaw=+40.3°   比例 +0.706
反的 wz=-0.5: 真值 Δyaw=-56.1°   odom Δyaw=-23.8°   比例 +0.425
```

**不对称**是特征：`/joint_states` 的 `position` 是连续角，越过 ±π 会翻回去（或反过来），
裸差分得到 ≈±2π 的假增量 —— 一步就注入 ±66° 的假转角，而 `|Δ|=6.28` 小于原来的跳变阈值 50，
过滤器抓不住。

**修法**（`scripts/mecanum_odom.py`）：差分前先在 ±π 处解缠绕
`d = (p - q + π) mod 2π − π`，跳变阈值同时从 50 收紧到 3.0 rad（缠绕 6.28；正常单帧增量 <0.1）。

**这个 bug 会骗人**：M2 的第一版判据用 /odom 算落点误差，5 次全部 0.054–0.062 m（"通过"），
而 Gazebo 真值误差是 1.73–1.85 m、朝向差 156°。**判据必须用真值**（已改）。

## 14. `ros2 launch` / `make` 与真值测试的几个坑（M2 阶段新增）

- **`BasicNavigator.waitUntilNav2Active()` 会死等 `amcl/get_state`**：我们这套定位是
  `odom + map->odom 恒等`（没有 AMCL），调用会无限刷 "amcl/get_state service not available"。
  传 `localizer="bt_navigator"` 即可跳过（同时绕过 `_waitForInitialPose`）。
- **`map->odom` 必须带出生点偏移**：odom 从 (0,0) 起算，而 `map` 里车在 spawn 位姿。
  恒等变换会让 Nav2 认为"起点在货架里"，规划成功但 recoveries 一路涨、车不走（实测 18.55 m 误差）。
- **两套 Nav2 同时活着会 bringup 失败**：`Failed to change state for node: controller_server`
  → `Aborting bringup`。重启前先 `pkill -f "[n]av2_"` 等一批；`m2` 脚本里也去掉了
  `nav.lifecycleShutdown()`（否则每跑一次都要重起整套 Nav2）。
- **判据脚本自己会"抖"**：`ign topic -e -t /clock` 偶发超时会让 `sim_now()` 返回 None，
  按 `if t is None: break` 写的话，"转 2 s"实际只转一瞬（表现为"底盘不转"的假象）。
  推进循环要有墙钟兜底。

## 16. M2 侧移入库位：真值比 odom 差 1.25 m，且收敛到一个"常量偏差"

**实测（三次不同动作拆解，每次 5 轮）**

| 配置 | 真值落点误差 | odom 口径误差 | 备注 |
|---|---|---|---|
| 原始（复合动作，vx 0.40 / wz 1.00） | 1.73–1.85 m | 0.054–0.062 m | 假通过 |
| SPEC §4.2 ② 降速（vx 0.25 / vy 0.20 / wz 0.50） | 1.22–1.28 m | 0.049–0.069 m | 降 30% |
| 动作拆成"回起点 → 原地转 → 纯侧移" | 1.27–1.34 m | 0.082–0.088 m | 没改善 |

**残差的结构**（终点 vs 目标 `(-18.0, -3.05, -90°)`）：`dx=+0.74, dy=+0.99, dyaw=+26.7°`，
5 轮之间波动 ±0.03 m —— 不是随机打滑，是**系统性偏置**。

**已经排除的**（都有实测证据）：
- odom 的轮角差分数学：轮子转 6.555 rad、底盘真值 +71.6°，用轮角算 +69.6°（差 2.8%）→ 正确。
- 轮角缠绕：gz 的 `axis1.position` 是连续弧度（实测 -7.22 rad，不缠绕）。
- 轮速与指令的一致性：vx 0.4 → 四轮 +3.9474；wz 0.5 → 2.697（与插件逆解一致）。
- `map->odom` 出生点偏移：已补（不补会 18.5 m）。

**还没排除的（下一步）**：
- 原地转向这一段，odom 记 -90° 而真值只到 -71°（**20% 少转**），但单独的纯转动测试只差 2.8%。
  差别在于 Nav2 的命令是"短促脉冲 + 反复修正"，怀疑每次起停的静摩擦/打滑会吃掉固定角度。
  → 可以测"连续 cos 型 wz 命令"与"MPPI 脉冲式 wz 命令"下的转角差，定位是控制器还是摩擦模型。
- `mu2=0`（辊子侧向完全无摩擦）是极端假设；真实麦克纳姆辊子有残余侧向摩擦，
  可以试 `mu2 = 0.1~0.3` 看常量偏差是否随之缩小。

**判据口径提醒**：M2 必须用 Gazebo 真值位姿判。odom 口径会给 0.05–0.09 m 的"优秀"结果，
而真实误差是 1.2–1.9 m —— 这是本轮最容易骗过人的地方。

## 18. 【致命】headless 不等于不渲染：传感器全开会挂死 nvidia-modeset，整台机器冻死

**现象**：跑一段时间后桌面无响应、屏幕打不开，只能断电。

**证据（断电前那次启动的内核日志）**
```
12:26:29  NVRM: Error in service of callback
12:26:30  nvidia-modeset: ERROR: GPU:0: Error while waiting for GPU progress: 0x0000c77d:0 2:0:4048:4040
          （此后每 5 s 一条，一直刷到关机）
```
- `journalctl -b -1 -k | grep -ci "out of memory|oom.kill"` = **0** → **不是内存不够**
  （机器 31 GiB，恢复后常驻仅 4 GiB，swap 2 GiB 一次都没用）
- 显卡：Intel i915（主显示）+ NVIDIA RTX 4080 Laptop（12 GiB）。**两者共用同一个
  `nvidia-modeset`**：仿真把 dGPU 弄挂，桌面一起死。

**根因链**
1. `gz sim -s` 只是"不画窗口"，**每个传感器照样渲染**。本设计的默认配置是
   3×640×480@15Hz 相机 + 1024×32@10Hz 激光 + 200Hz IMU，全部 `always_on=true`；
   即使用户没有订阅相机（bridge_images 关闭），gz 仍然每帧渲染。
2. 每次重起没有强制拆除，实测出现过 **2 个 `warehouse.sdf` 并存**，每个都新开一套
   GL/EGL 上下文，叠加加剧 dGPU 压力。
3. 点云 1 MB/帧 × 10 Hz = 10 MB/s 过 `ros_gz_bridge`，而桥只能吞吐 5.7 Hz →
   队列堆积（内存与延迟双爆）。

**三层护栏（已落地，缺一不可）**
- `make down` —— 一条命令拆干净整套栈；**每次重起前必须先跑**。
- `make sim` 前置 `scripts/stack_guard.py` —— 已有仿真在跑就拒绝再起第二套。
- `make sim` 自动带起 `scripts/gpu_watchdog.py` —— 内核日志一出现
  `nvidia-modeset: ERROR` / `NVRM:` 就立刻拆栈并存证到 `results/gpu_watchdog.log`，
  抢在桌面冻死之前（实测从第一条报错到冻死只有几分钟）。
- 传感器档位：`make robot`（默认 `SENSORS=nav`）= 相机 `always_on=false` + 激光
  360×16@5Hz；点云 1024 KB@10Hz → **180 KB@5Hz（11.4× 降低）**。
  只有 S1 这类要原图的判据才 `make robot SENSORS=full`。

**不要做的事**
- 不要用 `gz sim -s` 就以为"安全"；也不要在已有仿真的情况下再 launch 一套。
- 不要在循环里起 `ign topic -e -n 1` 之类的子进程去读 `/world/.../pose/info`
  （880 个模型，每读一次就是一次全量 dump；`truth_localization.py` 曾按 5 Hz 这么干，
  已改成需要时再读）。

## 17. M2 五轮配置对比：0.10 m 判据当前够不到，瓶颈是"横向漂移观测不到"

全部都是 **Gazebo 真值**落的点（不是 /odom）。

| # | 配置 | 真值落点误差 | 说明 |
|---|---|---|---|
| 1 | fdir1 + 复合动作，vx .40/wz 1.00 | 1.73–1.85 m | odom 口径 0.05–0.06 m（假） |
| 2 | + 降速 vx .25/vy .20/wz .50 | 1.22–**1.28** m | 目前最好 |
| 3 | + 动作拆成 回起点→原地转→纯侧移 | 1.27–1.34 m | 无改善 |
| 4 | mu2 0→0.2（残余辊子侧向摩擦） | 3.63–3.73 m | 长距离段向北飘、顶在货架面 |
| 5 | 完美定位（真值置换 map->odom） | 第 1 轮就 nav=False、18 次恢复 | 有了真实位姿后 Nav2 发现"车被顶住"，只能反复恢复 |

**机理（有实测支撑）**
- 车在长对角线（13 m，vx+vy 混合）上会**自己偏航/横漂**：单测 `cmd=(0.1,-0.15)` 4 s，
  mu2=0 时真值偏航 -9.8° 而轮系推算 0.0°；mu2=0.2 时这一项修好了，长距离反而更糟。
- 轮式 odom 只能看到轮子转了多少，**看不到横向漂移**。实测过"车顶在货架面上、轮子空转"的场景：
  真值位移 0.000 m 而 odom 累积 +0.686 m。所以 odom 闭环永远会"以为到了"。
- 没有雷达就没有任何能观测横漂的定位源（雷达桥问题见 §12），AMCL 无从谈起。

**四种自由度单测结论（同一位置，`body_motion_probe.py`）**
```
cmd (0.2, 0, 0)   轮系 +0.686  真值 +0.777 ~ +0.526   ✓ 前向准
cmd (0, 0.2, 0)   轮系 +0.652  真值 +0.655           ✓ 侧移准
cmd (0, 0, 0.3)   轮系 +58.4°  真值 +56.0°            ✓ 转向准
cmd (0.1,-0.15,0) 轮系 dyaw 0°  真值 -9.8°(mu2=0)     ✗ 混合运动有寄生偏航
```

**下一步三选一（需要决策，不是技术细节）**
1. **承认物理极限**：按 SPEC §4.2 ③ 把 M2 判据改成"侧移动作可完成 + 落点误差记录在案"，
   目前能给出的数是 1.2 m 量级（横向 0.9 m 位移本身是成功的）。
2. **提高物理保真度**：给轮子做真正的辊子接触（多圆柱/球近似）或用 `mu2` + 接触刚度联合标定，
   把寄生偏航压到可忽略，再回 0.10 m 判据。
3. **补上能观测横漂的定位**：先修雷达桥（§12），用 S1 的 2D 激光做 scan-matching 定位，
   这样 odom 漂了 Nav2 也能纠正 —— 这条路同时是 P4 的前提。

## 28. P6 接 LLM 后端（qwen2.5:7b）暴露的两个真问题

**背景**：P6 的 LANG-1 一直只有 rule 后端在跑（69/69）。把 `--backend ollama` 真跑一遍，
一次暴露两个问题，一个是代码 bug，一个是判据级的能力差距。

### 28.1 工具层没有校验边界：LLM 给个 `bay="F"` 就把整条基准跑崩

```
ValueError: invalid literal for int() with base 10: 'F'      # depot_vln/mock/world.py:87
```

qwen2.5:7b 把"去 F 巷…"里的巷道字母当成了 `bay` 的值。`resolve()` 里直接
`int(query["bay"])` → 异常冒到 langgraph 节点 → **整个 69 条基准中止**（不是那一条失败）。
规则 NLU 永远产不出这种值，所以这个洞一直没暴露 —— **换后端才炸，这是"边界不校验"的典型症状**。

**修法（根因，不是 try/except 兜住）**：在 `MockWorld.resolve()` 前加一层 `_sanitize()`，
把 LLM 的 query 当**不可信输入**处理：

* `kind` 不在白名单 → `UNKNOWN_INTENT`；必需字段缺失 → `UNKNOWN_INTENT`；
* `aisle` 必须是大写且在 A–F；`address` 必须在槽位表里；`bay`/`level` 必须是整数且落在范围内；
* 任何坏值 → 返回 `([], 拒绝码)`，**绝不抛异常**（与 LANG-1b"拒绝要带原因码"一致）。

**顺带踩到的第二个坑**：规则 NLU 会带 `level=None` / `side=None` 这样的键，
第一版 `_sanitize` 把"存在但为 None"当非法值 → 正常指令被判 `NO_SLOT`，
规则基线从 69/69 掉到 **43/69（62.3%）**。**None 的语义是"未指定"，不是错**：遇到就丢键。
（教训：给共享工具层加校验后，**必须立刻重跑基线**，否则会用新 bug 换掉老 bug。）

### 28.2 LLM 后端在歧义指令上**静默猜**，LANG-1a 判据不通过

| 后端 | 总计 | direct | attribute | ambiguous | unreachable | LANG-1a 静默猜错 | LANG-1b 拒绝缺码 |
|---|---|---|---|---|---|---|---|
| rule（基线） | **69/69 = 100%** | 18/18 | 18/18 | 15/15 | 18/18 | **0** | 0 |
| ollama qwen2.5:7b | **52/69 = 75.4%** | 18/18 | 11/18 | 12/15 | 11/18 | **3** | 1 |

关键不只是准确率低，而是**失败模式不安全**：M13/M14/M15（"去 A/B/C 巷最里面那个位"）
被直接送到 `reach/…-24-1`，即**不问就猜**——正是 LANG-1a 要拦的行为。
另外 U06（"去封住的那条 F 巷"）返回 `NO_SLOT` 而不是 `BLOCKED`，原因码用错。

**结论**：LANG-1 的 PASS 只能记在 rule 后端上；LLM 后端作为**对比项**如实入账，
两条安全判据均不通过。要让它可用，需要"结构化输出 + schema 校验 + 歧义时必须发问"的
约束层，而不是把裸 LLM 直接接进图。**这件事没做，记在 REPORT §5.7。**

### 28.3 换模型能不能救？（三个模型 + 同口径对比，2026-10-31 实测）

同一份 69 条基准、同一个 mock 工具层、`temperature=0`、`reasoning=False`（qwen3 系列），
唯一变量是模型：

| 后端 | 总准确率 | direct | attribute | ambiguous | unreachable | LANG-1a 静默猜错 | LANG-1b 缺码 | **单条延迟** | **JSON 解析失败→回退规则** |
|---|---|---|---|---|---|---|---|---|---|
| rule | 69/69 = 100% | 18/18 | 18/18 | 15/15 | 18/18 | 0 | 0 | 5 ms | — |
| qwen2.5:7b | 50/69 = 72.5%（另次 52/69） | 18/18 | 11/18 | 10/15 | 11/18 | 3 | 1 | **1.1 s** | 0 |
| qwen3-vl:8b | 52/69 = 75.4% | 18/18 | **6/18** | 11/15 | **17/18** | 2 | 0 | **34–56 s** | **16/69** |
| qwen3:latest | 33/69 = 47.8% | 18/18 | 5/18 | **0/15** | 10/18 | **8** | 4 | 0.61 s | 0 |

四个判读：

1. **总分没变**：75.4% 与 72.5% 的差在 run-to-run ±2 噪声内（qwen2.5 两次 50/52）。
   差别只在**分布**：VLM 在 unreachable（结构化拒绝）上强、在 attribute（"最里面/最多"这类
   空间推理）上弱。**没有"整体更强"这回事。**
2. **延迟是硬约束**：34–56 s/条 vs 1.1 s/条。全量 69 条跑 **64 分钟**（qwen2.5 是 2.3 s）。
   交互式机器人等不起 —— 这个差异比准确率 2 个百分点重要一个数量级。
3. **23%（16/69）的输出解析不出 JSON，静默回退到规则后端** —— 意味着 75.4% 里有四分之一
   不是模型答的。**"没统计回退率"的 LLM 跑分普遍偏乐观**（qwen2.5 是 0，VLM 是 16：
   VLM 倾向输出解释性文字，`re.search(r"\{.*\}")` 抓不干净）。
4. **两条安全判据三个模型全不达标**（静默猜错 3 / 2 / 8，要求 0）。所以**换模型不是 P6 的解**，
   约束层（结构化输出 + 歧义必须发问）才是。

**工程结论**：文本抽槽保持 `qwen2.5:7b`（快且准确率与 VLM 持平）；qwen3-vl:8b 按原设计
用在 **verify（图像复核）** 环节 —— 那里 20–30 s/次是可接受的。命令：
`MODEL=qwen3-vl:8b BACKEND=ollama make bench-run`（结果落 `results/bench_llm/`，
不进 `results/` 根目录，避免被 `accept.py` 的 `latest("bench_2*.csv")` 记进 LANG-1 的账）。

## 27. S3 双目视觉里程计：从"ATE 32 m"到"沿光轴退化"的归因链（以及一次差点误判的测量事故）

**现象**：S3（rtabmap stereo_odometry → slam_toolbox）跑完 202.5 m 路线，11 路点全到、
1181 帧全有估计，但 **ATE 32.4 m / 终点漂移 54.4 m / 地图一致 27.1%**。
同时图像侧一切正常：rtabmap 处理 5809 帧、quality 中位 413、无 tracking lost。

**归因方法（可复用）**：链上有两段，只看 `map→base` 分不清是谁坏 ——

```
rtabmap stereo_odometry  ->  odom -> base_footprint    （视觉能不能测出运动）
slam_toolbox             ->  map  -> odom              （激光建图把 odom 掰回来没有）
```

`scripts/s3_diag.py` 同时记**真值 / 视觉 odom / 建图 map→base** 三条轨迹，走"进巷 + 沿巷 20 m"：

| 段 | 几何 | 视觉还原率 |
|---|---|---|
| leg1（11 m，横通道进巷，含横向分量与转向） | 97–104% | ✅ 精度极高 |
| leg2（20 m，**沿巷纯前进**） | **0%** | ❌ 只在这一种运动上崩 |

yaw 误差 −2.5°。→ 病因在视觉的"沿光轴平移"，与建图后端无关。

**逐项排除（都实测过，别再重复）**

| 怀疑 | 实测 | 结论 |
|---|---|---|
| slam_toolbox 掰坏 odom | 只读 odom→base 就已经 0.42 | 排除 |
| 估计器选型（GFTT/BRIEF 帧到地图） | 换帧到帧 + SIFT：0.36 | 排除 |
| 左右目无视差 | 左右目帧差 10–16 灰度 | 排除 |
| 左右目不同步 | 戳差 **0.0 ms**（`cam_always_on:=true`） | 排除 |
| 软件光栅 / 没 GPU | gz 映射 `libnvidia` 45 处、`/dev/nvidia0` 打开、`swrast/llvmpipe` 0 处 | 排除 |
| 帧率不足 | 唯一帧 4.81 Hz 墙钟 ≈ 11 Hz 仿真时钟（配置 10 Hz），1168 帧零重复 | 排除 |

**定案**：货架每 2.4 m 完全重复（同一贴图平铺），相机朝巷前进时画面近似"平移不变"，
特征匹配到任意一格都成立，最优解是"没动"。属**景物周期性导致的观测退化**，
不是参数问题 → 按项目原则重构世界（见 DECISIONS D12）。

**⚠️ 一次差点误判的测量事故（最贵的一课）**

诊断脚本最初在驾驶循环里只靠 `rclpy.spin_once(node, timeout_sec=0)` 采样（每 5 s 的进度回调里
才转一次）。订阅队列 depth=3 在 10 Hz 下 0.3 s 就溢出 → **120 s 只收到 38 帧**，于是算出
"画面 20 秒才更新一次、唯一帧 0.05 Hz"，几乎把结论带偏成"gz 渲染挂了"，为此白跑了
三次渲染探针（还都抓错进程：`make → /bin/sh -c → ruby → ign gazebo` 四层包装器，
前三层 cmdline 里都带 `warehouse.sdf`）。

修正：**后台线程常驻 `rclpy.spin`**，驾驶循环里只 `time.sleep`。同一测量立刻给出
1168 帧 / 唯一帧 4.81 Hz / 帧间差 1.91 —— 与前一次结论完全相反。

**新增纪律（第 6 条测量链自检）**：除"真值起点自检 / 估计帧覆盖 >95% / 闭环 ≥2 Hz /
路线 100% 跑完 / 指标有合成自检"之外，还要
**证明订阅端的采样方式能跟上发布率** —— 否则测到的是自己的采样率，不是信号本身。
判据：`收到帧数 / 时长 ≈ 发布率`（本例 1168/243 s ≈ 4.8 Hz 墙钟 = 10 Hz 仿真 ✓）。

**顺带修掉的四个真 bug**（都不是病因，但都会让 S3 根本出不了 odom）

1. 图像 `header.frame_id` 是 gz 作用域名（`depot_bot/base_footprint/stereo_left`），TF 树里没有 →
   `scripts/image_frame_relay.py` 改写成 `stereo_left_link`。
2. `camera_info` 用节点钟打戳 → 与图像戳差 10⁹ 量级，approx_sync 永远配不上 →
   改成**照抄图像的 header 戳**（且每帧只发一对，避免"重复戳"被 rtabmap 丢弃）。
3. rtabmap 的 odom 原本 remap 到 `/odom`，与 mecanum_odom（~250 Hz）撞车 →
   改发 `/odometry/visual`（实测混用时读数 18 倍偏差，其实是车顶着货架空转）。
4. `cam_always_on:=false` 时两台相机的 update 相位从"各自被订阅那一刻"起算，永远差一帧
   （戳差 100 ms）→ 改 `cam_always_on:=true`（同一仿真步出图，戳差 0.0 ms），
   同时 `enable_rgbd:=false` 减掉一个渲染器。

### 27.1 五次尝试的对照表（这是 S3 结论的全部依据）

| # | 配置变化 | leg1（横向/转弯） | **leg2（沿巷前进 20 m）** | 整体比值 | 备注 |
|---|---|---|---|---|---|
| 1 | 基线：平铺混凝土 + 特征匹配 + 无 IMU | 87–107% | **0%** | 0.418 | 视觉位置整段冻住 |
| 2 | 唯一地面纹理（稀疏斑点）+ 特征匹配 | 87–107% | **22%** | 0.507 | 前进首次"有读数" |
| 3 | 唯一地面（稠密角点 120k）+ **KLT 光流** | 95–102% | **0%** | 0.418 | 光流在重复地面锁错对应 |
| 4 | 唯一地面 + 特征匹配 + **IMU 融合**（真·双目惯性） | 91–102% | **0%** | 0.425 | IMU 主要稳姿态，不补线速度 |
| 5 | 第 4 项 + **速度 ×2.6**（每帧 2.5 cm → 9 cm） | 92–100% | **0%**（且末段 **yaw −177.8°**） | 0.384 | 提高信号 3.5 倍无效，还别名成掉头 |

**结论（写进报告）**：沿光轴平移的不可观测性**与每帧位移大小无关**（提高 3.5 倍无效）、
**与纹理唯一性无关**（唯一地面只把 0% 抬到 22%，且不稳定）、**与 IMU 无关**（融合后仍 0%）、
**与对应方式无关**（光流更差）。而横向/转弯始终 95–107%。

机制：相机沿巷道轴平移时，图像上主要表现为**径向缩放**，而缩放量在 2–10 m 处的特征上只有
1–3 px；同时走廊沿轴是**近周期结构**（bay 每 2.4 m 同构、两侧货架镜像相似），
于是"前进一格"与"没动"在特征层几乎等价 —— 速度一快就直接别名成 180° 翻转。
这是**景物的观测退化**，不是 rtabmap 参数、不是渲染、不是同步、不是建图后端。

**按项目纪律的处置**：连续三次以上尝试无效即停手（不盲试），S3 记 **未达标**，
报告按 SPEC 要求写清"视觉在哪里失败"，**不删除 S3、不伪造达标**。
唯一地面纹理（D12）仍然保留 —— 它让横向/转弯稳定在 95–107%、并修正了世界"处处一样"的
生成缺陷，本身是正确的，只是不足以让沿轴可观测。

4. **转场必须显式路由，而且"选哪一侧横通道"不能只看 x 正负**：直线 `drive_to` 会斜穿货架；

  **118 组**里同一块空间有 2 个以上货位同时判"占用"，真值自相矛盾 → 答案键本身是错的。

  （托盘 0.90→0.52、carton_l 0.60→0.52，否则探到另一侧又会被对侧看见）。
  修完 576 → **288 个物理多边形**（每组 2 个 = 上下层共用 footprint，物理正确）、**0 组**矛盾。
- 新增硬闸门 **G0 货位物理空间唯一**、**G0b 同层同空间不重复占用**（`make world` 22 项全 PASS）。
- 碰撞几何未变（货物是 `collision=False` 纯视觉）→ M2 / SLAM-1 / SEG-1 结论不受影响
  （map-check 5 项、390 碰撞体、287/288 入库点与修前完全一致）。

**B. 五个判据坑（每个都曾把分数打到 0.1–0.7）**

1. **相机的 +0.265 m 前伸量**：相机装在车体前缘，到货架面 1.335 m（不是车体中心到面的 1.6 m）。
   深度带按 1.6 设 → 货物前表面（1.18–1.40 m）被切在门外，recall 只剩 **0.09**。
2. **前景判据方向**：货位在货架**内部**。空货位会穿透看到下一巷道（6–11 m），有货则在 1.2–1.4 m 有前表面。
   写成"比货架面更近"会把地面和立柱都算成货。
3. **宽度不能用量像素跨度**：转向误差 20°/35° 会把投影宽度虚高 6%/22%，而三种纸箱只差 0.15–0.20 m。
   改成逐像素换算世界 x、取 1/99 分位跨度（3/97 分位会系统性吃掉 10% 宽度，也是一份错）。
4. **扁平物体没有高度跨度**：托盘 h≈0.00，被"h ≥ 0.05"整类挡掉；托盘宽 1.05 m 又被"w ≤ 0.90"挡掉。
   两个约束都是自己设错的 → 现在 w 上限 1.15、h 允许 ≈0，且 `w > 0.85` 一律判托盘（没有纸箱比 0.70 宽）。
5. **透过空货位能看到对侧巷道的货**（最后一个误检源，5 个全中）：世界 x 相同，只有深度不同。
   实测本侧货物前表面 `d_med = 1.18–1.40`，对侧货 `1.76–1.79`，中间有 0.36 m 空档 → 深度带上界切在 **1.55**。
   5 个误检逐一核对：每个的对侧 bay 确实都有货。

**C. 转向残差是横向归属的第一误差源（控制层面）**

- 纯 P 律（`wz = 1.5·err`，上限 0.5）：大角度冲过头（残差 **10–35°**）、小角度被四轮静摩擦
  （mu=3.0）吃掉（2–4° 反复超时）。
- 只用脉冲式：每脉冲 ≤ 0.9 s × 0.25 rad/s ≈ 13°，转 180° 要 14 个（预算只有 6 个）→ 残差 **58–135°**。
- **两段式**才成：P 律粗转到 10° 内 → 停稳 → 脉冲精修到 2°。实测 46 帧残差多数 0.1–2.0°
  （少数 3–11°），横向散布从 ±0.5 m 收到 ±0.1 m，误检随之清零。

**已知限制（写进报告）**：上层货位（level 2）在这台车上**物理不可见** —— 相机高 0.436 m、
第 2 层层板在 1.75 m，从下向上被层板下沿遮挡（该带 1.6 m 处像素占 0%、全在 5.9 m 穿透）。
SEG-2 只评下层 288/576 个货位，上层记"未评"（既不算漏检也不算通过）。
要覆盖上层需把观测位后移或把相机升高（硬件/布局改动）。

**方法学备注**：类别阈值和深度分水岭都来自实测簇（`carton_s` w≈0.35/h≈0.17、`m` ≈0.48/0.26、
`l` ≈0.67/0.39，托盘 h≈0 且 w≈1.0），不是照抄 config 的标称尺寸 —— 实测高度只有标称的 ~0.65 倍
（遮挡 + 相机姿态偏差）。深度上界 1.55 落在 0.36 m 的物理空档中央，不是贴着噪声边缘挑的。

**元教训（比这条数本身重要）**：测量链坏掉时，产生的偏差**看起来非常像物理现象** ——
我当时据此写下"等距重复巷格导致整 bay 跳格（2.4 m）"的结论，而实际是"闭环 0.19 Hz + 真值通道错位"。
规则：**任何"物理结论"之前，先证明测量链是干净的** —— ①真值通道有起点自检 ②估计帧覆盖率 >95%

- slam_toolbox 的**地图**来自位姿图优化后的节点位姿，`map->base_footprint` 是实时修正量 ——
  两者可以"图很准、逐帧位姿抖"，所以判 SLAM 必须同时报地图一致性与 ATE。
- 这一轮确实调过 4 个 slam 参数（`correlation_search_space_dimension` 0.5→0.30、
  `minimum_travel_distance` 0.3→0.45、回环响应 0.45→0.55 / 0.35→0.40）。定版结果是在这组参数下取得的，
  但没有做"参数 A/B"，不能声称参数是改善的原因。

**余下的话留给 S2/S3**：S1 已经是 0.356 m / 203 m，S2（+IMU EKF）与 S3（双目惯导）要证明的是
"能不能更好、以及代价"；如果 S2/S3 没有改善，也是一个有效结论。

**历史记录（已作废的判断，留作反面教材）**：v1 首跑曾得出 ATE 3.579 m / 一致性 44.3%，并据此写下
"沿轴整 bay 跳格"的病因。看过 v6 之后这条判断作废 —— 原因是判据链（TF 覆盖率 49%、闭环 0.19–0.77 Hz、
真值通道）、不是扫描匹配。**不要再引用 v1–v3 的 ATE 当作 SLAM 质量指标。**

## 21. AMCL 在这条长直巷道里比纯 odom 更差（实测，别再当"解法"）

**动机**：M2 五轮落点误差单调变差（0.059→0.081→0.123→0.125→0.135），逐段看是
"回起点"的真值残差每轮涨 1.5–2 cm —— 系统只有轮式里程计，`map->odom` 是固定常量 −31。

**做法**：`config/amcl_omni.yaml` + `launch/localization_amcl.launch.py`
（`robot_model_type: nav2_amcl::OmniMotionModel`，静态图 + `scan_relay` 抽的 `/scan`，
`set_initial_pose` 给出生点）。`m2_static_run.sh` 用 `LOC=amcl` 切换。

**结果（更差，已否证）**：5 次落点误差 **0.191 / 0.458 / 0.361 / 0.481 / 0.587**，成功 0/5；
而同一批数据里 odom 与真值只差 0.02–0.07（odom 是准的），**是 AMCL 的 `map->odom` 自身带着
0.1 → 0.55 m 的沿 x 偏置**，Nav2 于是停在离目标半米的地方还以为到了。

**原因**：与 SLAM-1 的结论同源 —— C 巷这类长直巷道沿轴（x）几乎无可观测特征
（两面平行墙 + 2.4 m 等距立柱），单环 `/scan` 的扫描匹配在沿轴方向无法分辨，粒子云沿 x 滑。
**沿轴可观测性不解决，AMCL/SLAM 都救不了沿轴定位。**

**处置**：`m2_static_run.sh` 默认 `LOC=static`（odom + 固定 map->odom），AMCL 仅作对照；
长度轴定位的真解在 P4：要么 3D 特征（ICP/LIO），要么在世界里加沿轴可观测的地面标记/立柱端面。

## 20. 【流程】地图从"清单"派生，漏掉世界里的障碍物（M2 白排查两天的真正原因）

### 现象
M2 五轮全部 `nav=True recoveries=0`，odom 口径 0.09 m（"完美"），真值恒定 0.93 m；
x 端准、y 端系统性短 0.5–0.9 m；同一位置量前向兑现率只有 0.05、位移还偏到 45°。

### 根因（两层）
1. **地图 ⊂ 世界**：静态图当时只从 `world/layout.json` 刷货架，而叉车/周转箱/护栏是世界
   生成器另写的（`config/world.yaml: obstacles`）。Nav2 于是不知道 C 巷 bay 5 右侧有东西。
2. **点位没做碰撞检查**：`m2_side_dock.py` 用 `bay.center_x + 观测位偏移` 直接算出
   (−18.00, −3.05)，而叉车车身占 y∈[−3.01, −2.39]、x∈[−18.53, −17.28] —— 机器人从
   y=−2.15 侧移过去，在 −2.39 被顶住；轮子照转、odom 照记，于是"odom 到位、真值差 0.93 m"。

### 为什么没早发现（这才是要点）
- SPEC 把"地图与真值的占据一致性"写成 **SLAM 的事后评价指标**，从未写成 **生成地图的硬约束**；
- P0 纪律是"一条命令一个判据"，但"世界↔地图↔点位"这条判据**当时根本不存在**；
- 排查中我曾用 `layout.json` 里没有 forklift 来否定"叉车挡路" —— **用不完整的清单做否定判断**，
  直接把方向带偏到摩擦/打滑/MPPI 上两天。

### 现在的防线（都已实现）
- `scripts/depot_geometry.py`：世界几何的唯一解析入口（SDF 静态碰撞体 / 点位计算），
  地图生成与点位校验共用同一份口径。
- `scripts/make_static_map.py`：占据只来自 SDF 静态碰撞体（390 个），生成后立即自检。
- `scripts/map_check.py` + `make map-check`：独立闸门（地图覆盖世界、点位可用、逐点判定一致）。
- `make world` 自动重建地图并校验；`scripts/m2_static_run.sh` 开跑前强制过闸门（FAIL 拒绝跑）。
- `m2_side_dock.py` 默认 `--bay 4`，并在启动时用 `blockers_at()` 拒绝落在障碍里的点位。

### 可复用到其它项目的教训
1. **单一真值源**：凡从世界派生的产物（地图/点位/路线/评测真值），都从**构建产物**派生，
   不要从"配置清单"派生 —— 清单迟早和产物不一致，而且没人会发现。
2. **一致性必须做成一条可复跑的判据**，并挂在构建链上（生成后立刻跑），而不是靠人记得看。
3. **否定结论要用完整数据源**："某个清单里没有" ≠ "世界里没有"；先查生成链输入或直接查产物。
4. **验收点位必须在启动时做碰撞检查**，让错误以 1 秒的 FAIL 暴露，而不是 5 轮 × 8 分钟的"数据异常"。

## 29. robot_localization 输出 NaN（`invalid quaternion (nan nan nan nan)`）

S5（地面光流+轮速 EKF）第一次接的时候，EKF 起来了、30 Hz 在发，但位姿全是 NaN，
日志里两句话各说了一半：

```
TF_DENORMALIZED_QUATERNION: Ignoring transform for child_frame_id "base_footprint" ...
                             because of an invalid quaternion in the transform (nan nan nan nan)
[ekf_filter_node]: Critical Error, NaNs were detected in the output state of the filter.
                   This was likely due to poorly coniditioned process, noise, or sensor covariances.
```

排下来是**三个独立的坑**，每个都能单独造成 NaN：

### 29.1 传感器协方差全 0 = 在 RL 里等于"绝对确信"

`gz` 的 IMU 三个 covariance 阵列全是 0；`mecanum_odom` 的 `twist.covariance` 也是全 0；
我自己新写的 `floorflow_odom` 干脆没填。RL 要求测量协方差可逆，全 0 是奇异矩阵。
**规范**：位姿 x/y 给 2 cm（4e-4）、速度给 2 cm/s（4e-4）、不融合的轴给大值（1e-3/5e-2），
IMU 的 `orientation_covariance[0] = -1`（表示"不提供绝对姿态"）。
中继节点 `image_frame_relay.py` 现在负责补齐 IMU 协方差。

### 29.2 `relative: true` 会造成"自引用 TF"

RL 的 `odomN_relative: true` 要把测量换算到相对第一帧，需要查
`odom -> base_footprint` —— 而这个 TF 的唯一发布者就是 EKF 自己
（视觉节点 `--publish-tf 0`、仿真 `odom_tf:=false`）。自引用 → 发散/NaN。
**规范**：两路都发 odom 系下的绝对位姿时用 `relative: false`，RL 按协方差加权，本来就支持。

### 29.3 "IMU 明明在发，EKF 却当它不存在"

S2 一直用 `/imu`（原始桥接话题），它的 `header.frame_id` 是 gz 作用域名
（`depot_bot/imu_link` → 全局 `/depot_bot/imu_link`），而 `robot_state_publisher` 发的是 `imu_link`
→ **TF 查不到，RL 静默丢掉这一路**（不报错！）。所以 S2 的"加 IMU 没改善"有一条隐藏解释：
IMU 从头到尾没进过滤器。S5 改喂中继后的 `/imu_tf`（frame 已改写）之后，IMU **第一次真的进来**，
29.1 的零协方差才暴露出问题。

**排查手法**：`print_diagnostics: true` 会逐路打印 received / queued / accepted。
**代价教训**：这三个变量是我一次全加进去的（新协方差 + relative + 换话题），
第一轮失败后要拆开验证 —— **一次只引入一个"独有变量"**。

### 29.4 真正的元凶：僵尸节点污染（`pkill -P` 只杀直接子进程）

上面 29.1–29.3 修完之后 NaN **仍然出现**，日志还有个奇怪签名：同一份文件里出现
**NUL 空洞**（`\0\0\0…`）和**两套不同速率的状态行**（`35.3 Hz`、位姿 `(+28.17,−35.23)`）。
那是"另一个进程还在往同一个 fd 写"的铁证 —— 后面偏移写出来的区域就是空洞。

实测残留：**3 个 `ekf_node` + 1 个 `floorflow_odom`**，都是前三次冒烟留下的。
它们在 `/odometry/floorflow` 和 `/odometry/filtered` 上同时发布（其中一路带着另一个仿真
会话的记忆），EKF 收到互相矛盾的两组位姿 → NaN。

**为什么收不掉**：`EXTRA_NODES` 从单条命令变成 wrapper 脚本后，进程树变成
`nohup bash` → `bash -lc` → `bash s5_nodes.sh` → `ekf_node`（四层），
而收尾只做 `pkill -9 -P $EXTRA_PID`（**只杀直接子进程**）→ 孙进程全部变孤儿。

**规范**：
1. 附加节点一律 `nohup setsid ...` 起，自成进程组；收尾用 `kill -9 -$EXTRA_PID`（负数 = 整组）；
2. 再 `pkill -P` + `kill` 兜底，最后按名字 `[f]loorflow_odom.py` / `[e]kf_node` 扫一遍并打印警告；
3. **起跑前也扫一遍**（`s3_smoke.sh` 开头），别指望上一轮收干净；
4. 判据脚本只报告"数字"，**不保证数字来自唯一发布者** —— 怀疑数值异常时，
   先 `pgrep -c -f` 数发布者，再看算法。

**代价教训**：这一轮我在配置上连改三处（协方差、relative、IMU 话题），
其实三次失败里有两次是僵尸进程造成的。**改配置前先确认运行环境干净**，
否则会把环境噪声当成算法缺陷去修。

## 33. 前向安全层与 verify 的两个"看不见"（2026-11-02）

### 33.1 侧向 0.25 m 的障碍不会触发前向安全层——这是设计，不是 bug
测试：`UTT="去 C-L-08-1" GUARD=1 NOLANE=1 make p6-demo`，沿 C 巷中线（y=−2.15）经过 bay 5 的
静态叉车（占 y∈[−3.00,−2.40]）。**安全层压住 0 次**，机器人安全通过。
算一下就知道必然如此：障碍在侧向 0.25 m。要落进 ±25° 扇区，需前向距离 ≥0.25/tan25° = 0.54 m，
此时**斜距** = √(0.54²+0.25²) = 0.59 m > 0.55 m 阈值；再靠近，方位角就超出扇区了。
→ 前向扇区对"擦肩而过"天然是盲区。

**不要改成"走廊判定"**（|横向|<半宽 就算威胁）：机器人一旦停在叉车旁边，横向 0.25 m、
前向 0 → 判定永远是"挡住" → **死锁**。窄处通行必须由车道偏移/规划器解决，
安全层只做"前方突然出现东西就停"这一件事。

### 33.2 verify 出现假阳性：空位被报成"有货"
`C-L-08-1` 真值 `occupied: false`，地图（WMS 台账）也说空，**VLM 报 `carton_s` conf 0.8**。
核对过世界侧：`world/warehouse.sdf` 的 `cargo` 模型里 **没有** `cargo_C_L_08_1`，
只有 `cargo_C_L_08_2`（z=2.03，第二层）→ **世界与真值一致，是观测错了**。
图的 `verify` 节点因此给出 `VERIFY_MISMATCH`（地图 vs 观测不一致）——逻辑是对的，
但它能报对，靠的是**地图先验**，不是视觉本身。

### 33.3 真因：货架是**通透**的，目标格背后 2.2 m 的货投影到了画面正中心

先说被推翻的猜测：一度怀疑"相机 FOV/外参与配置不符"（因为按 1.0–1.6 m 视距推不出
一帧能看到 5 列 × 2 层）。核对后 **xacro 的 HFOV 就是 90°、`cam_z=0.35`、`cam_pitch=0`，
相机模型没问题**。真正的原因是**开放式货架没有背板** —— 相机透过目标格看到了后面的巷子。

把 `world/warehouse.sdf` 里 `cargo` 模型的全部 link（pose 是**绝对坐标**，573 个碰撞体）
用同一套相机模型投影到 320×240 上，落在画面内的有 **54 件**，最近几件的投影是：

| 货物 | 视距 | 投影 (u,v) |
|---|---|---|
| `cargo_D_R_08_1` | **2.21 m** | **(167, 120)** ← 画面正中心（cx=160, cy=120）|
| `cargo_E_R_08_1` | 6.53 m | (160, 118) |
| `cargo_D_L_07_2` | 6.35 m | (96, 76) |
| `cargo_D_L_09_2` | 6.41 m | (229, 74) |

目标格 `C-L-08-1` 是空的、且通透 → **它正后方 2.2 m 处 D 巷的货恰好落在画面中心**，
VLM 于是把"画面中央的纸箱"当成目标格里的货，报 `occupied, carton_s, conf 0.8`。
"5 列 × 2 层"也是同一原因：6–7 m 外的 D/E 巷货架整个填满画面。

**这也解释了为什么前面 3 次都对**：目标格有货时，目标货物在**最前面**、遮住背景；
空位时背景货顶上来 —— 典型的**遮挡顺序问题**，不是置信度问题。

**由此定下的修法（不改世界、不调提示词）**：verify 必须带**深度门限**。
现有硬件就够（双目基线 0.12 m、`/stereo_left` + `/stereo_right`）：
① 把目标格的三维多边形按位姿投影成图像四边形；② 只保留落在四边形内**且视差深度落在
目标深度带**（≈1.0–1.6 m）的像素；③ 背景（2.2 m 以远）被深度门限剔掉；④ 再判占用/裁剪问 VLM。
一条判据性推论：**空位的正确结果应该是"看不见货"，而不是"看见了背景"。**

### 33.4 verify 三改判据的教训：判据选错时，自检会"帮你说谎"

第一版：**带内像素比例**（`[d_front-0.05, d_back+0.10]` 内占比 ≥6%）。
→ 空位 `C-L-08-1` 判成有货，占比 **10.6%**。原因：货架的板条/立柱端面就落在带内。
**合成自检全过**，因为我造的"空位"是纯背景，没有货架结构 —— 自检用例太理想化。

第二版：**最大连通块占比**（货是一整块面、货架是细边）。
→ 空位 1.5% / 有货 2.5%，阈值 2%：**余量只有 1.67 倍**，靠它等于赌命。

第三版（定稿）：**比格口更近的像素数**。
物理含义直接：空格里没有任何东西比格口更近（恒 0），有货就有（536/1434 px）。

三条可复用的规矩：
1. **判据要有物理含义**，不要用"落在区间内的比例"这类间接统计量 —— 它会把背景纹理算成目标。
2. **合成自检必须包含"真实场景里存在的干扰物"**（本例是货架边框），否则自检只会证明你的假设。
3. **自检要喂真实链路的输入类型**：`depth` 到运行时是 `np.ndarray`，`if depth:` 会抛
   `truth value of an array is ambiguous`；我自检喂的是 `list`，于是白跑了两轮仿真才炸。

### 33.5 观测窗口不能取整格宽：位姿误差会把邻格的货框进来
按整格 2.4 m 投影，四边形平移 14 px（≈偏航偏 4°）后空位从 **0 px 变 535 px**（框到隔壁格的货）。
收到 ±0.70 m 后，15 种扰动（du=±7/±14 px、dv=±8 px）下空位恒 **0 px**、有货最低 **186 px**。
→ 抗位姿误差靠的是**窗口留白**（窗口边缘距邻格货 ≥1.5 m），不是靠调阈值。

### 33.6 把传感器数据落盘，把"跑仿真"变成"离线标定"
`VERIFY=depth` 的 demo 会把 `left / right / depth / 投影参数 / 位姿` 存到
`results/depth_dumps/<addr>_<ts>.npz`。此后 `scripts/verify_depth_audit.py` 可离线复算全部判决，
并做"四边形平移 → 判决是否翻转"的鲁棒性检验。
本轮改了 3 次判据/阈值，只有 2 次需要重开仿真（拿新样本），其余全离线 —— 省的是**人的等待时间**。

### 34. "事件计数为 0"必须先证明**进程活着**（前向安全层全程未运行）

`scripts/forward_guard.py` 在 `Node()` 之后裸调 `node.declare_parameter("use_sim_time", True)`，
抛 `ParameterAlreadyDeclaredException: ('Parameter(s) already declared', ['use_sim_time'])`
→ **每次启动即崩**。而 `p6_demo.sh` 的判据只是 `grep -c '正在压住' results/p6_guard.log`，
崩掉的进程自然给出 **0** —— 于是把"0 次压住"读成了"正常行驶不插手"，还写进了报告。

**受影响的结论（已作废/待重测）**
- "假阳性检查过：`GUARD=1` 正常行驶压住 0 次" → **空结论**（安全层当时没在跑）。
- "以 0.25 m 侧向掠过静态叉车时压住 0 次" → 同上。几何论证（落进 ±25° 扇区需前向 ≥0.54 m、
  届时斜距 0.59 m 已超 0.55 阈值）**独立成立**，但那次"实测"不算数。

**规矩**
1. **`declare_parameter("use_sim_time")` 一律包 try/except**（本项目第 4 次踩这条）。
2. **任何"0 次事件"型判据必须先加活性检查**：起完进程后 `grep` 一行已知的启动日志
   （本例 `[GUARD] 就绪：…`），没有就让整轮作废（`exit 6`），绝不输出"0 次 = 正常"。
   同一逻辑适用于"0 丢帧""0 次重试""0 个越界"这些反证型指标。

## 35. 避障试验台自身的五个坑（全部是静默失败）

调 Nav2 绕行时，我踩到的**一半问题不在 Nav2 里，而在我自己写的试验台里**。它们的共同特征是
**不报错、只是给出一个错的结论**，所以逐条记下来。

### 35.1 名字里带 `nav2_` 的脚本会被自己起的栈杀掉
`m2_static_run.sh` 的 `kill_nav2()` 用 `pkill -f "[n]av2_"` 按**命令行**匹配。我的试验台叫
`nav2_avoid_probe.sh` → 起栈时被自己的栈 `pkill` 掉，输出停在"起 Nav2 栈"、连超时提示都
来不及打（看起来像"栈起不来"）。**结论：脚本名/日志名一律不要含 `nav2_`。**
（`p6_demo.sh`、`m2_static_run.sh` 恰好都不含，所以这个坑只在新建脚本时出现。）

### 35.2 `while cond: ... else:` —— 条件一开始为假时 `else` 照样执行
用 `--trigger 0` 跳过"等机器人靠近"这个循环，写成 `while args.trigger > 0 and ...: ... else: 超时退出`。
结果 `trigger=0` 时条件立即为假 → **`else` 分支照跑** → 立刻"超时放弃"退出，车根本没造出来。
正确写法：`if trigger > 0: while ...` 分开。

### 35.3 `Goal was rejected` —— `READY` ≠ 全部节点 active
`m2_static_run.sh` 的 `READY` 只保证 **`bt_navigator`** active。lifecycle manager 是逐个激活的，
此时底下还没有 `controller_server` / `planner_server` 的 action server → 目标被**直接拒收**
（`Goal was rejected`，而不是"等待"或"超时"）。**发目标前必须轮询三个节点的 `ros2 lifecycle get`
全是 `active`**，并对拒收做重试。

### 35.4 参数没传 ≠ 参数默认值合理（`--block-y` 漏传导致假阳性）
试验台按"起点→目标直线"算出推车应放在 `y=-0.80`，但调用 `move_obstacle.py` 时**漏传
`--block-y`** → 脚本用的是"该巷行驶线"`y=-1.60`。机器人沿斜线走时从车北侧 0.44 m **擦过**，
于是被判成"绕过"（假阳性）。**教训：位置这类参数必须在日志里回读**（`早检通过：推车位姿
(-26.00,-0.81)` 那一行就是用来干这个的，它当场戳穿了错误）。

### 35.5 costmap 致命格探针解析失败 —— **已修**（`scripts/costmap_probe.py`）

**原症状**：`ros2 topic echo --once /local_costmap/costmap` + 正则解析，两条 costmap 都打印"读不到"，
8 s 超时。看起来像 topic 不存在或权限问题，实际有三条叠加：

1. **`/local_costmap/costmap` 是 160×160 = 25600 个 int**，`topic echo` 逐行打印成 YAML 列表，
   序列化+打印+管道常超过几秒 → **超时返回空**（调用方只看到 `None`，没有任何提示）。
2. **QoS 不兼容**：Nav2 的 costmap publisher 用 `transient_local`，`ros2 topic echo` 默认
   durability 不对齐，**可能一条都收不到**（而 `topic info` 仍显示有 publisher，更容易误判）。
3. **正则要在一堆数字里区分** `info.origin` / `position` / `data`，容易串。

**修法**：改成 rclpy 直接订阅（`scripts/costmap_probe.py`），QoS 显式对齐
`RELIABLE + TRANSIENT_LOCAL`，**独立进程**（不与主流程 spin 挤 context），输出一行 JSON。

**验证**：`--selftest` 7/7（离线，不需要 ROS）——用**宽≠高**的栅格、不对称坐标、原点偏移、
`-1`/低代价值、空数组六个角度验证索引换算，防止把行主序或 x/y 写反。
接入点：`move_obstacle.sample_costmap_at()`（保留原签名，内部改为调这个脚本）。

### 35.6 度量口径：不要用"路径 y 的 min/max"判绕行
两次被斜线骗：`plan y 范围 -2.17~-1.57`（从当前位置到目标的直线本身）、`-1.62~-0.87`
（同理）都被读成"绕行"。**唯一可靠的量是"路径在障碍 x 处的 y 与障碍 y 之差"**，
且要求 ≥0.5 m 且机器人确实越过障碍（双条件）才算绕行。

## 36. `make` 会把退出码归一成 2 —— 0/3/1 的契约在 make 后面失效

本项目的判据契约写在**退出码**上（`p6_demo.py`）：`0` 到达且核验一致 / `3` 到达但观测与真值不符
（`PASS_WITH_WARN`）/ `1` 失败。但如果你用 `make p6-demo` 去跑：

```
make: *** [Makefile:108：p6-demo] 错误 3      ← 真值 3 只出现在这行文字里
$ echo $?
2                                            ← $? 拿到的是 make 自己的失败码
```

GNU make 对任何配方失败都返回 **1 或 2**，不会透传子进程的退出码。**实测踩到**：演示脚本里
写 `make p6-demo; echo "退出码=$?"`，期望 3，实际打出 2，看起来像"判据没按约定分类"。

**结论**：
- 要**判退出码**时直接跑 `bash scripts/p6_demo.sh`（或 `.venv/bin/python scripts/p6_demo.py`）。
- 日常用 `make` 没问题，但看的是脚本自己打印的 `[p6] demo 退出码 3` 那一行，不是 `$?`。
- 同理适用于 `accept.py`、`avoid_probe.sh` 等所有靠退出码表达状态的入口。

## 37. "路径偏出"不能单独当避障证据 —— 必须做无车对照

我两次把**静态地图本来就有的绕行**误判成"绕开了障碍"，两次都是同一个根：

| 版本 | 度量 | 错在哪 |
|---|---|---|
| 第一版 | `plan` 点的 y 的 min/max | 斜线路径本身就跨越很大 y 范围（假 `BYPASSED`）|
| 第二版 | 路径在障碍 x 处的 y 与"出生点→目标"弦的差 | **规划是从机器人当前位置出发的**，弦不成立 → 无车也偏 0.45 m；且按弦摆的车**不在真实路径上** |

**唯一可靠的做法是配对实验**：

1. `CONTROL=1 bash scripts/avoid_probe.sh` → 无车基线（同一起飞点/目标/采样）
2. `bash scripts/avoid_probe.sh` → 有车
3. 判据：`|有车偏出| − |无车偏出| ≥ 0.5 m` **且** 车仍挡路时机器人越过

**摆车位置不能由几何"算"出来**（弦、巷中线都不行），要由**对照实测**决定：机器人经过该 x 时
实际在哪个 y，车就摆哪个 y。旁证检查：`/scan` 最近回波应该在 ~1 m 量级；若是 2 m+，
说明激光那一圈根本没扫到车，实验从原理上就不成立。

`accept.py` 的 P6-2f 已改成配对判据（缺对照 → "未跑"），不再接受"单组偏出 ≥0.5 m"。

### 37.1 靶标诊断不能用"全向最近回波"
`/scan` 取全局 min 会被**侧向货架**占住（走廊里恒约 2.2 m），于是"车放 3 m 远"和"车放 5 m 远"
读出来都是 2.2 m，看起来像"看不见"。**要取靶标方位角 ±5° 内的回波**。
实测（`scripts/scan_target_probe.sh`）：2.0 m 处读到 **1.78 m**（预期 1.69）→ 看得见；
1.0 m 那两行 `nan` 是 `ros2 topic echo` 8 s 超时，需要重试。

### 37.2 `set -u` + `source /opt/ros/humble/setup.bash` + `2>/dev/null` = 一声不响退出码 1
ROS 的 setup 脚本里有未定义变量，`set -u` 把展开错误变成致命错误，而 stderr 又被 `/dev/null` 吞掉 →
现象是"命令跑完什么都没打印、退出码 1"，看起来像脚本没被执行。**本项目脚本一律只用 `set -o pipefail`。**

## 38. 两层 costmap 必须**分别**验证（同一个障碍，一层标上一层没标）

实测：同一个推车（车心 1 m 半径内），`/local_costmap` 最近致命格 **0.08 m**（标上了），
`/global_costmap` **0.48 m**（没标上，0.48 > 车半宽 0.26），而两者的 `obstacle_layer` 配置"看起来"
几乎一样（都是 `/scan` + `LaserScan` + marking/clearing）。

**现象链**：全局规划器（全局 costmap）看不见 → 规划穿过障碍的直线；局部控制器（局部 costmap）
看得见 → 拒绝执行 → **停滞或擦蹭**。表面看像"Nav2 不会避障"，实际是等长的一层坏了。

**做法**：`scripts/costmap_probe.py` 分别探两层，**看 `min_d`（最近致命格距离）而不是个数** ——
个数在半径 1 m 内容易把隔壁货架算进来；只有 `min_d ≈ 0`~半个障碍尺寸才是"标上了本体"。

**符号陷阱**：odom 帧的目标点必须 `odom = world − SPAWN_X`（本项目 = world + 31）。
写成 `world + SPAWN_X` 会去查 x−62 处的空白区域，报出"0 个致命格"，看起来像"这层失效"。

## 40. 车体斜 45° 沿巷道"平移"（不是转弯，是横着走）

**现象**：Nav2 巡航时车体相对巷道斜约 45°，沿路径平移，视觉上像"漂着走"。

**判据**（先量再改，别看截图）：滑移角 = 车体系里速度矢量与车头 +x 的夹角

```
slip = |atan2(vy_body, vx_body)|
slip ≈ 0°   正常（车头朝哪走哪）
slip ≈ 45°  斜着走      ← 本症状
slip ≈ 90°  纯横移
```

测量：`.venv/bin/python scripts/cmd_audit.py --seconds 90 --csv results/nav_cmd_log.csv`
（或 `make cmd-audit`）。它只订阅 `/odom`，不发控制。

**根因**：MPPI 用 `motion_model: Omni`，而"车头对准路径切向"只由 `PathAngleCritic` 一项表达，
它的权重（2.0）远低于 `PathAlignCritic`（14.0）；`PreferForwardCritic` 又按设计是 0。
于是最优解 = 车头不动 + 横移贴路径。**这不是底盘错了，是代价函数没有表达业务约定。**

**修法**（SPEC §4.4 / DECISIONS D32）：

| 参数 | 改前 | 改后 | 说明 |
|---|---|---|---|
| `PathAngleCritic.cost_weight` | 2.0 | **20.0** | 与 PathAlign 同量级并再压一档（目标滑移 <2°）|
| `vy_std` | 0.20 | **0.05** | 横移候选采样大幅收窄（不禁用）|
| `PreferForwardCritic.cost_weight` | 0.0 | 0.0 | **保持**，横移能力要留 |
| `vy_max` | 0.14 | 0.14 | **保持**，M2 侧移贴靠要用 |

**验收**：滑移角 **中位 ≤ 2°**、90 分位 ≤ 5°、>20° 样本 ≤ 1%。

**禁止的修法**：把 `vy_max` 设 0。那是砍功能治症状 —— 全向底盘的横移是选型理由
（M2 侧移入库 ≥0.8 m），砍掉只是把问题挪到别处。

## 41. 车开到东墙也不停——`map->odom` 写死"车在出生点"，而 odom 已被手动驾驶污染

**现象**（2026-11-03）：`make nav-to X=-10.80 Y=-2.15` 目标在 C 巷 bay08，结果车一路向东
顶到东墙（实测真值 **x=+33.02, y=−4.23**，世界东墙 x=+33.5），`send_goal` 430 s 超时。

**实测证据**（仿真在现场，直接量出来的）：

```
/odom      = (+4.518, -20.089, +112.8°)
真值位姿    = (+33.024, -4.280,  -0.1°)
→ odom 相对世界：位置差 30+ m、航向差 113°
```

**根因**：`static_map_pub.py` 的 `map->odom` 原来**写死** `(-31, 0, 0)`（＝出生点），
前提是"起栈瞬间车正好在出生点、odom 从 0 起算"。而 `mecanum_odom` 是从**仿真启动**起
累计的：手动开过、撞过叉车、贴墙蹭过之后，odom 已经攒了 30 m 位置误差 + 113° 航向误差。
于是

```
Nav2 以为车在 pose_map = odom + (-31,0) = (-26.5, -20.1)   ← 已经在地图 y 范围(±20)之外
目标 (-10.80, -2.15) 被它在"自己的地图坐标系"里解释
→ 它认为走到了，物理上却向东跑了 44 m
```

**修法**（已落地并现场验证）：

* `static_map_pub.py` 改为按真值锚定：`t = truth − R(Δ)·odom`，`Δ = truth_yaw − odom_yaw`；
  车在出生点时该式**退化为 (-31, 0, 0)**，与旧行为逐位一致（M2/SLAM 判据不受影响）；
* **同步读**，不要后台线程 + `spin_once` 混用（第一版那样写，25 s 内两个读数都没拿到，
  静默回退固定偏移 → 又错一次）；
* 读数与结果都打日志：`读数 OK：odom=(...) truth=(...)`、`按真值算 map->odom = (...)`；
* `nav_to.sh` 增加自检：回退到固定偏移直接 **exit 9 拒绝跑**；偏移不等于出生点时打印
  "odom 已被手动驾驶污染，录制/判据前请重起仿真"。

**现场验证**：同一台仿真上跑 `static_map_pub.py` →

```
读数 OK：odom=(+4.518,-20.089,+112.8deg) truth=(+33.024,-4.280,-0.1deg)
按真值算 map->odom = (53.289, -7.929, -1.9702 rad)   # ≡ Δyaw −112.9°
```

代入后 `pose_map` 恰好等于真值 `(33.024, −4.280, −0.1°)` ✓。

**纪律**：判据/录制一律从**干净仿真**开始（`make down` 后重起）—— 这样 odom 从 0 起算，
`map->odom` 恒为出生点值，坐标系没有任何模糊空间。

## 42. Nav2 一路开过头 16 m、贴着货架面滑行 —— 轮式里程计在 20 m 内漂 15.6°

**现象**（2026-11-03）：`make nav-to X=-10.80 Y=-2.15`，`bt_navigator` 日志明确记
`Begin navigating from (-31.00, 0.00) to (-10.80, -2.15)`，但车一路向东，真值跑到
**x=+5.0**（目标 −10.8，过头 16 m）、y=−3.49（贴住南侧货架面 −3.75），427 s 超时。

**实测（同一次运行，真值 vs odom）**：

```
真值   (+5.013, -3.494, -4.6°)
odom   (+36.045, -4.595, -20.2°)      # odom + (-31,0) = (+5.05, -4.60)
误差   dx 0.03 m ✓   dy 1.10 m ✗   航向 15.6° ✗
```

**机制**：横向误差把车带进货架块的 y 范围，车一面顶货架面、一面被 MPPI 持续给前进速度，
于是"沿面滑行"：odom 一直在涨（进度检查器认为在动，不触发恢复），但离目标永远差一点。
更早一次同源故障里 odom 航向误差达 **113°**。

**修法**：

1. `LOC=truth`（`nav-to` 默认）：静态图只发 `/map`（`--no-tf`），`map->odom` 由
   `scripts/truth_map_odom.py` 以 **2 Hz** 按 `truth − R(Δ)·odom` 持续校正 →
   Nav2 的位姿误差被压到"2 Hz 内的漂移"（毫米级）。现场验证：`已发布 10 次（跳过 0）`。
2. `nav_to.sh` 收尾 `zero_cmd()`：拆栈前发一次零速 `Twist`。**mecanum 插件会一直保持
   最后一条速度指令**，实测拆栈后机器人仍在滑行（RTF 低时看起来像卡住，其实还在走）。

**定位精度本身不由这条链路代表**：S5/EKF（ATE 0.227 m）与 AMCL 是 P4 的正经评估；
真值锚定只用于仿真里的"驾驶 + 语义 + 读编号"演示，与 P6 的 `POSE=truth` 同源。

## 43. RTF 掉到 1.76%、Nav2 服务大面积超时 —— Gazebo GUI 在用 Intel 核显软件渲染

**现象**：`make nav-to` 卡在"起栈"不返回（6 分钟无输出）；`ros2 lifecycle get /controller_server`
= active，`/planner_server` 服务**不响应**，`/bt_navigator` = **inactive**；GUI 右下角 RTF = **1.76%**。

**实测**：

```
ps:            ign gazebo gui   272% CPU     ign gazebo server  173% CPU
/proc/.../maps: /iris_dri.so                  ← GUI 走的是 Intel 核显的 Mesa 驱动
nvidia-smi:    0% 利用率, 15 MiB, 1.33 W      ← RTX 4080 完全闲置
xrandr:        Provider 0 = modesetting(Intel) 驱动 eDP-1 2560x1600
               Provider 1 = NVIDIA-G0（可作为 offload provider）
```

本机是 Optimus 结构：X 屏挂在 Intel 上，默认 GL 上下文跟着落在核显。用核显软/弱渲染
2560×1600 + 3500 个带贴图物件 → RTF 1.76%，physics server 被 GUI 挤占 → Nav2 的
定时器/服务调用按仿真时间计全部超时（`planner_server` 不响应 → lifecycle 激活失败）。

**两个独立问题**：
1. 渲染走错 GPU（本条目）
2. `nav_to.sh` 里 `ros2 lifecycle get` **没有 timeout**，服务不响应时永久挂住 → 已修
   （全部 ros2 CLI 调用加 `timeout 6`，等待循环每 10 s 打印进度，失败时打印三节点实际状态）

**修法（按风险从低到高）**：

* **A（推荐，零 GPU 风险）**：跑 headless，RTF 回到 ~0.44
  `make sim SIM_ARGS='gui:=false'`。要画面就录相机话题 `/camera/image_raw`（ffmpeg），
  不必开 Gazebo GUI。
* **B**：把 GUI 显式绑到 RTX 4080
  `__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia make sim SIM_ARGS='gui:=true'`
  起来后必须用 `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv` 确认
  **显存 > 500 MiB**；仍是 15 MiB 说明离屏渲染没生效，退回 A。
* **C**：降渲染量（只画 level-1 编号牌 / 去掉吊带 / 缩窗口 / 240 Hz → 60 Hz）。

**判据**：`ign gazebo gui` 的 CPU 应 < 120%，RTF ≥ 0.25，`planner_server` 的
`ros2 lifecycle get` 在 2 s 内返回 active。
